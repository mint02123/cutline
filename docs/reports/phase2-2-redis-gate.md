## 한 줄 요약
**관문은 품절자를 MySQL 앞에서 돌려보내고 재고 행 UPDATE를 정확히 1,000번으로 줄였다. 하지만 품절 응답이 빨라진 것은
가상 스레드를 켠 뒤였다(품절 p95 6.03초 → 0.94초).** 산 사람의 응답은 빨라지지 않았고, 매진까지 시간은 오히려 늘었다.
측정 중 Redis 장애 복구 경로와 오픈 판정에서 버그 3개를 찾아 고쳤다.

## 방법
- 시나리오와 환경은 1단계 기준선과 같다 (4 vCPU 한 대에 k6·앱·MySQL·Redis, 커넥션 풀 10, 구매자 3,000명, 재고 1,000개, 오픈 ±0.5초에 도착).
- 측정일마다 환경이 흔들리므로 **같은 시간대에 네 가지를 번갈아 3회씩** 쟀다 (관문 끔 → 플랫폼 스레드 → 가상 스레드 → Redis 다운 순서를 3번). 표의 값은 3회의 중앙값이다.
- "관문 끔"은 2-1(품절 선판정)까지의 상태다. 이번 실행에서 다시 재 같은 시간대 비교 기준으로 쓴다.
- "Redis 다운"은 오픈 2초 뒤 Redis 컨테이너를 3초 동안 `docker pause`한다. 연결은 살아 있고 응답만 없는 상태라 명령마다 500ms 시간 초과가 난다.

## 해석
### 1. 관문은 일을 했지만, 품절자는 스레드를 기다렸다
관문을 켜자 재고 행 UPDATE가 1,220회에서 정확히 1,000회로 줄었다. 품절자 2,000명은 MySQL에 한 번도 닿지 않았다.
그런데 플랫폼 스레드에서는 품절 p95가 6.03초에서 4.78초로 21%밖에 줄지 않았다.

이유는 요청 스레드다. 관문을 통과한 1,000명은 커넥션 풀 10개를 기다리며 Tomcat 스레드 200개를 모두 쥔다.
관문에서 수백 마이크로초면 끝날 품절자도 스레드를 얻을 차례를 기다린다. 줄이 DB 커넥션 앞에서 스레드 앞으로 옮겨 갔을 뿐이다.
가상 스레드에서는 기다리는 요청이 스레드를 붙잡지 않으므로, 품절자는 도착하자마자 관문에서 답을 받는다 (p95 0.94초).

### 2. 가상 스레드의 대가: 산 사람이 더 기다린다
가상 스레드에서는 주문 성공 p50이 3.21초에서 4.45초로, 매진까지 시간이 6.71초에서 7.58초로 늘었다.
플랫폼 스레드에서는 스레드 200개가 자연스러운 입장 제한 역할을 해 커넥션 풀을 기다리는 요청이 최대 200개였다.
가상 스레드에서는 관문을 통과한 1,000개가 한꺼번에 커넥션 풀을 기다린다. 첫 주문이 들어간 시각도 오픈 뒤 69ms에서 835ms로 늦어졌다.
대기자가 많을수록 커넥션 경쟁 비용과 CPU 경합(k6·앱·MySQL이 4코어를 나눠 씀)이 커진다고 보지만, CPU 표본을 뜨지 않아 확인하지는 못했다.

가상 스레드를 기본값으로 정했다 (ADR-011). 2단계의 첫 목표가 "품절된 사람을 즉시 돌려보내는 것"이고,
3,000명 중 2,000명이 품절자다. 산 사람의 대기는 2-3 대기열이 입장 수를 제한해 다룰 문제다. 대기열은 관문을 통과해 커넥션을 기다리는 요청 수를
입장 속도로 묶으므로, 가상 스레드의 대가였던 "1,000개가 동시에 커넥션 경쟁"도 함께 사라질 것으로 본다. 2-3 측정에서 확인한다.

### 3. 매진까지 시간은 관문으로 줄지 않는다
관문을 켜도 매진 시간은 줄지 않았고 오히려 늘었다 (4.66초 → 6.71초). 매진까지 시간은 재고 행 하나를 쥐는 시간(주문당 약 5ms)이 정하고,
관문은 그 줄에 설 사람을 고를 뿐 줄 자체를 빠르게 하지 않는다. 관문을 켰을 때 더 늘어난 이유는 아직 설명하지 못했다.
같은 측정에서 관문을 끄면 오픈 직후 3ms 만에 첫 주문이 들어가지만 관문을 켜면 69ms가 걸렸고, 오픈 전 재시도가 211회에서 867회로 늘었다
(관문이 오픈 전 요청을 바로 돌려보내 클라이언트가 더 자주 다시 누름). 이 차이가 CPU를 나눠 쓰는 단일 호스트에서 매진을 늦췄을 가능성이 있다.
설계 문서대로 매진 시간은 1차 목표가 아니며, 2-4(재고 행 분할) 결정 때 CPU 표본과 함께 다시 본다.

### 4. Redis가 3초 멈춰도 판매는 계속되고 정합성은 지켜졌다
오픈 2초 뒤 Redis를 3초 동안 멈췄다. 그 사이 요청은 MySQL 경로(품절 선판정 + 조건부 UPDATE)로 처리됐고,
서버당 동시 20개 제한에 걸린 요청도 2초 안에 자리를 얻어 503은 0건이었다.
품절 p95(5.50초)는 관문을 끈 상태(6.03초)와 비슷하다. 장애 동안은 2-1 수준으로 돌아간다는 ADR-010의 예상과 맞다.
관문 건너뛰기 창은 실행마다 90~107번 열렸다. 멈춘 동안 이미 Redis에 보낸 명령들이 시간 초과를 낸 수만큼이다.

## 측정이 찾은 버그 3개
처음 측정(`p2d5-*`)에서 Redis 다운 3회가 모두 정합성 체커에 걸렸다. 테스트로는 드러나지 않던 문제였다.

### 버그 1: Redis가 돌아온 직후 토큰이 MySQL보다 많았다 (토큰 303개, 남은 재고 0)
Redis가 멈춘 동안 MySQL 경로로 팔린 주문은 토큰을 쓰지 않는다. Redis가 돌아오면 토큰은 멈추기 전 값 그대로라 MySQL 남은 재고보다 많다.
불변 조건(토큰 ≤ 남은 재고)이 깨진 상태로, 관문은 MySQL에 없는 재고로 사람을 들여보낸다. 초과판매는 조건부 UPDATE가 막지만
들어간 사람은 커넥션을 기다렸다가 품절을 받는다. 재동기화(5초 주기)가 고치기 전까지 이 상태가 이어졌다.

**수정**: MySQL 경로로 주문이 만들어진 드롭을 표시해 두고, 관문을 다시 쓰기 전에 토큰을 MySQL 남은 재고로 낮춘다.
표시는 커밋 뒤에 하므로, 낮추기가 아직 커밋되지 않은 주문을 놓쳐도 다음 요청이 다시 낮춘다.
(`OrderAdmissionService.clampIfSoldWithoutGate`, 테스트 `GateFailureTest`)

### 버그 2: 낮춘 토큰이 다시 살아났다 (끝난 뒤 토큰 41~73개)
버그 1을 고친 뒤에도 매진 뒤 토큰이 남았다. 관문을 통과했는데 MySQL에서 품절로 실패한 요청이 토큰을 돌려줬기 때문이다.
불변 조건이 지켜지면 토큰을 가진 요청은 MySQL에서 품절일 수 없다. 품절이 났다는 것은 토큰이 MySQL보다 많다는 뜻이므로,
이때 토큰을 돌려주면 없는 재고의 토큰이 되살아나 다음 사람도 헛걸음한다.

**수정**: 관문 통과 뒤 MySQL 품절이면 토큰을 돌려주지 않고 남은 재고로 낮춘다. 다른 실패(한도, 오류)는 그대로 돌려준다.
(`OrderAdmissionService.soldOutAfterAdmit`, 테스트 `StockGateTest`)

### 버그 3: 오픈 직후 1초 동안 관문과 MySQL이 서로 다른 답을 했다 (재고 행 UPDATE의 30%가 헛걸음)
관문을 켰는데 재고 행 UPDATE가 1,000회가 아니라 1,429~1,573회였고, 그만큼 롤백이 있었다.
관문은 오픈 시각이 되면 바로 통과시키는데, MySQL 조건부 UPDATE는 `status = 'OPEN'`도 요구했다.
상태는 오픈 스케줄러가 1초마다 바꾸므로, 그 사이 관문을 통과한 요청은 재고 행 잠금을 잡았다가 "오픈 전"으로 롤백했다.
토큰은 돌려받고 클라이언트는 다시 눌렀다. 첫 주문이 오픈 뒤 약 0.9초에야 들어간 이유다.

**수정**: 판매 가능 여부를 상태가 아니라 오픈 시각으로 정한다 (`status IN ('SCHEDULED', 'OPEN') AND opens_at <= now`).
상태 변경은 스케줄러가 뒤따라 하는 표시로 둔다. 닫힌 드롭(`CLOSED`)은 여전히 팔리지 않는다. 고친 뒤 재고 행 UPDATE는 정확히 1,000회,
첫 주문은 오픈 뒤 69ms였다. (ADR-002 수정 메모, 테스트 `StockGateTest`)

| | 고치기 전 (`p2d5-*`) | 고친 뒤 (`p2d5f-*`) |
| --- | --- | --- |
| 관문 켬: 재고 행 UPDATE / 롤백 | 1,429~1,573회 / 429~573회 | 1,000회 / 0회 |
| 관문 켬: 첫 주문까지 | 0.91~1.36초 | 0.06~0.13초 (플랫폼 스레드) |
| Redis 다운: 끝난 뒤 토큰 / 남은 재고 | 171~374 / 0 (체커 위반 3/3) | 0 / 0 (체커 통과 3/3) |
