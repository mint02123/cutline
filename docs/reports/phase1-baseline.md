# 1단계 성능 기준선: MySQL만으로 버틴 드롭 오픈

- 측정일: 2026-11-24
- 대상: `main` (1단계 8일차까지), Redis·대기열 없음
- 재현: `cd load-test/k6 && BUYERS=3000 STOCK=1000 ./run-baseline.sh` (원자료: `load-test/results/`)

## 한 줄 요약
**정합성은 완벽했고, 속도는 재고 행 하나가 정했다.** 구매자 5,000명이 몰려도 초과판매, 5xx, 정합성 위반은 0이었다.
그러나 재고 1,000개가 팔리는 데 약 5초(초당 약 200건)가 걸렸다. 품절된 사람은 "품절" 응답을 받기까지 중간값 6~7초를 기다렸다.
커넥션 풀을 늘려도, 디스크 동기화를 꺼도 빨라지지 않았다. 모든 요청이 `drop_event` 행 하나의 잠금 앞에 한 줄로 서기 때문이다.
이 수치가 2단계(Redis 1차 관문, 대기열)의 "전" 기준선이다.

## 시나리오
`load-test/k6/drop-rush.js`
- 구매자 N명(가상 사용자 1명 = 1명)이 오픈 시각 ±0.5초 안에 도착해 주문한다. 재고 1,000개, 1인 한도 1개.
- 오픈 직후 "아직 안 열림"(`DROP_NOT_OPEN`, 오픈 스케줄러 1초 주기)이면 0.2초 뒤 다시 누른다. 이 응답은 지연 통계에서 뺀다.
- 주문에 성공한 사람의 80%는 1~3초 뒤 결제한다(가짜 PG, 지연·장애 없음). 20%는 떠난다(10분 뒤 만료).
- 끝나면 `GET /internal/consistency`로 정합성 체커 6개 규칙을 확인한다.
- 측정 전에 별도 드롭으로 구매자 500명 워밍업을 한 번 돌리고 버린다(JIT, 커넥션 풀 예열).

## 환경
| 항목 | 값 |

| 배치 | k6, 백엔드(JVM 힙 1GB), MySQL 8.4(docker) **모두 같은 호스트** |

부하 발생기와 서버가 CPU를 나눠 쓰므로 절대 수치는 이 환경에서만 의미가 있다.
같은 스크립트로 같은 환경에서 다시 재서 **전후를 비교하는 용도**로 쓴다.
AWS 측정(5단계)에서는 부하 발생기를 분리한다.

- 매진까지 = 오픈 시각부터 마지막 주문이 만들어진 시각까지 (`sellout.txt`).

- 모든 실행에서 주문은 정확히 1,000건이었다. 초과판매, 이중 결제, 환불 누락, 미해결 결제는 0이었다.

## 병목 분석
### 1. 커넥션 풀을 늘려도 빨라지지 않는다
구매자 3,000명 기준:

| 풀 크기 | 매진까지 | 주문 전체 p50 | InnoDB 행 잠금 대기 합계 |
| --- | --- | --- | --- |
| 10 | 5.19초 | 5.64초 | 52초 |
| 30 | 5.28초 | 5.99초 | 228초 |
| 50 | 5.63초 | 6.75초 | 456초 |

풀을 늘리면 대기 장소만 바뀐다. 앱의 커넥션 대기열에 있던 요청이 DB 안의 행 잠금 대기열로 옮겨 갈 뿐이다.
잠금 대기 합계가 풀 크기에 비례해 늘었고, 지연은 오히려 조금 나빠졌다. (풀 30·50은 성공/품절 지연을 나누기 전 스크립트로 측정)

### 2. 디스크 동기화도 원인이 아니다
`innodb_flush_log_at_trx_commit=2`, `sync_binlog=0`으로 커밋마다 하던 fsync를 끈 진단 측정에서도 매진까지 5.49초로 같았다.
(진단용일 뿐이다. 운영에서는 내구성을 위해 1을 유지한다.)

### 3. CPU도 꽉 차지 않았다
오픈 구간에서 CPU 유휴가 16~35% 남았다. 같은 호스트의 k6가 CPU를 나눠 쓰는 것은 수치를 키우는 요인이지만, 병목 자체는 아니다.

### 4. 원인: 재고 행 하나에 모든 요청이 줄을 선다
`performance_schema` 문장별 통계 (구매자 3,000명):

| 문장 | 실행 | 평균 | 잠금 대기 합계 |
| --- | --- | --- | --- |
| `UPDATE drop_event SET remaining_qty = remaining_qty - ? WHERE ...` | 3,481 | 15.2ms | **52.0초** |
| `COMMIT` | 2,623 | 2.2ms | 0 |
| `ROLLBACK` | 2,481 | 1.8ms | 0 |
| 그 외 (한도 upsert, 주문 INSERT, 멱등 키 등) | - | 0.1~0.7ms | 수 ms |

잠금 대기는 거의 전부 재고 UPDATE 한 문장에서 나왔다. 주문 한 건은 이 행의 배타 잠금을 잡은 채
한도 upsert, 주문 INSERT, 멱등 키 갱신, 커밋까지 끝내야 잠금을 놓는다(트러블슈팅 002에서 정한 잠금 순서).
매진까지 1,000건에 약 5초이므로, **한 건이 행을 쥐는 시간은 약 5ms**이고 이것이 처리량의 상한이다.

### 5. 품절된 사람도 같은 줄에 선다
품절 응답이 성공 응답보다 느리다(3,000명: p50 6.3초 vs 3.4초).
REPEATABLE READ에서 `UPDATE ... WHERE remaining_qty >= ?`는 조건이 거짓이어도 행을 잠그고 롤백할 때까지 쥔다.
재고가 0이 된 뒤에도 남은 2,000~4,000명이 한 명씩 잠금을 잡았다 놓으며 "품절"을 확인한다.
"아직 안 열림" 재시도 요청도 같은 행을 잠근다.

### 6. 결제도 덩달아 느려진다
결제는 `drop_event`를 건드리지 않는데도 p95가 2.8초에서 7.9초로 구매자 수를 따라 늘었다.
커넥션 10개를 주문 요청들이 잠금 대기하며 쥐고 있어서, 결제 요청이 커넥션을 받지 못하기 때문이다.
**핫 로우 하나가 무관한 기능까지 굶긴다.**

## 2단계에서 할 일 (이 기준선과 비교할 항목)
| 개선 | 노리는 지표 | 기대 |
| --- | --- | --- |
| 재고가 0이면 잠금 없이 바로 품절 응답 (읽기 전용 확인) | 품절 응답 p50 | 수 초 → 수십 ms. 가장 싸고 효과가 큰 첫 수 |
| Redis Lua 1차 관문 (재고 카운터, 한도) | 매진까지, 품절 응답, DB 잠금 대기 | 재고 수만큼만 DB에 도달. MySQL은 최종 확정만 |
| 대기열 (입장 토큰) | 결제 p95, 5xx | 동시에 DB에 닿는 요청 수 제한 → 결제 커넥션 확보 |
| (검토) 재고 행 분할 | 처리량 | 행 N개로 나눠 잠금 경합 분산. Redis 관문과 비교해 결정 |

## 원자료
`load-test/results/<실행이름>/`

- `sellout.txt`: 오픈 후 첫 주문, 매진 시각
- `statement-digest.tsv`: 문장별 실행 횟수, 평균·최대 시간(ms), 잠금 대기(ms)
- `mysql-status-before.tsv`, `mysql-status-after.tsv`: InnoDB 행 잠금 지표

- `environment.txt`: 측정 환경
