# ADR-007: 도메인별 패키지 모놀리스로 시작

- 상태: 채택
- 날짜: 2026-11-24

## 맥락
기획서는 최종적으로 앱 4개(대기열 API, 주문·결제 API, Outbox Relay, 정산 배치)를 EKS에 올린다.
하지만 1단계의 목표는 정합성 증명과 기준선이다. 혼자 개발하므로 분산의 복잡도를 감당할 이유가 생길 때 나눠야 한다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 처음부터 마이크로서비스 | 최종 구조와 같음 | 주문·재고·결제가 서비스 경계를 넘으면 분산 트랜잭션·사가가 1단계부터 필요. 측정 전에 복잡도부터 생김 |
| 계층형 모놀리스 (controller/service/repository) | 익숙함 | 도메인 경계가 안 보여 나중에 나누기 어려움 |
| **도메인별 패키지 모놀리스** | 한 DB 트랜잭션으로 정합성을 단순하게 증명. 경계는 패키지로 미리 드러남 | 공유 DB. 모듈 간 결합이 생기기 쉬움 |

## 결정
`com.cutline` 아래에 `seller`, `drop`, `order`, `payment`, `consistency`, `common`을 둔다. 모듈 사이는 아래 두 방식으로만 연결한다.
- **인터페이스**: 결제는 `PaymentGateway` 뒤의 PG만 안다(가짜 PG ↔ 토스페이먼츠 교체).
- **이벤트**: 결제된 주문 취소 → `OrderRefundRequested`(커밋 후) → 결제 모듈이 환불한다. 주문 모듈은 결제 모듈을 모른다.

## 결과와 포기한 것
- 재고·한도·주문이 한 트랜잭션이라 초과판매 0을 DB 제약과 조건부 UPDATE만으로 증명했다.
- 이미 생긴 결합 지점 (분리할 때 먼저 끊을 곳):
  - `payment`가 `orders` 테이블을 직접 잠그고 바꾼다 (`PaymentTransitions`).
  - `OrderExpiryService`가 `payment` 테이블을 직접 읽는다 (UNKNOWN 제외).
  - 정합성 체커는 모든 테이블을 조인한다. 분리 후에도 운영 검증용으로 남긴다.
- 다시 볼 조건: 2단계 대기열은 트래픽 특성이 달라(대기 연결 수만, 상태는 Redis) 별도 앱으로 가장 먼저 분리한다.
  주문·결제 분리는 3단계 Outbox 도입 때 결정한다.
