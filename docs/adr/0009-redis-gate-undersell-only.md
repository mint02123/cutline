# ADR-009: Redis는 1차 관문, 어긋나면 덜 파는 쪽으로

- 상태: 채택
- 날짜: 2026-11-25

## 맥락
품절 선판정(ADR-008)만으로는 품절 응답이 매진 시각 근처에 왔다. 구매자 대부분이 재고가 남아 있을 때 도착해,
누가 이길지가 MySQL 재고 행 잠금 줄에서 한 명씩 정해졌기 때문이다. 승자를 DB 밖에서 빠르게 정해야 한다.
동시에 MySQL이 최종 판단이라는 원칙(ADR-001)은 지켜야 한다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **Redis Lua로 입장 토큰을 원자적으로 감소, 통과한 요청만 MySQL 트랜잭션** | 거절은 Redis 왕복 한 번. MySQL 원칙 유지 | Redis와 MySQL 두 곳의 수량이 어긋날 수 있음 |
| Redis를 재고의 원본으로 (MySQL은 나중에 비동기 반영) | 가장 빠름 | Redis를 잃으면 판매 기록을 잃음. 초과판매 방어선이 Redis 하나 |
| `DECR` 한 번 (Lua 없이) | 단순 | 회원 한도와 오픈 시각을 함께 원자적으로 볼 수 없음 |

## 결정
- 키 `gate:{dropId}`(토큰, 한도, 오픈 시각)와 `gate:{dropId}:bought`(회원별 통과 수량). 해시 태그로 같은 슬롯.
- Lua 한 번에 오픈 시각 → 회원 한도 → 토큰 순으로 보고, 모두 통과하면 토큰을 줄인다.
- 키가 없으면 MySQL에서 적재한다(판매 예정·판매 중인 드롭). 회원별 수량은 적재하지 않는다. 잃으면 MySQL 한도가 막는다.
- **불변 조건: 토큰 수 ≤ MySQL 남은 재고.** 이를 위해
  - 관문을 통과하지 않은 요청은 MySQL 주문 경로로 보내지 않는다.
  - 통과했는데 MySQL에서 주문이 만들어지지 않으면 토큰을 돌려준다.
  - 만료·취소로 MySQL 재고가 돌아오면 **커밋 뒤에** 토큰을 돌려준다.
- 멱등 재요청은 관문이 거절했을 때, 그 회원이 관문을 통과한 적이 있을 때만 DB에서 확인한다.
- Redis에 닿지 못하면 관문 없이 MySQL 경로(ADR-008 선판정 + 조건부 UPDATE)로 처리한다.

## 결과와 포기한 것
- 예비 측정(구매자 3,000명, 1회): 재고 UPDATE는 정확히 1,000번만 실행됐다(1단계는 3,481번). 토큰과 MySQL 남은 재고가 함께 0으로 끝났다.
- 예비 측정에서 불변 조건이 깨지는 버그를 찾았다. 오픈 전 요청을 MySQL로 보냈더니, 그 사이 드롭이 열려 토큰 없이 팔리고 토큰이 44개 많아졌다.
  오픈 시각 판정을 관문으로 옮겨 고쳤다 (`StockGateTest`).
- 포기한 것: Redis를 잃으면 재적재 전까지 이미 산 회원도 관문을 통과한다(MySQL이 막는다). 돌려주지 못한 토큰은 덜 파는 상태로 남는다.
  재동기화 작업과 정합성 체커 규칙은 다음 단계에서 추가한다.
- 관문이 거절을 빨리 해도, 통과한 요청이 요청 스레드를 쥐고 DB 커넥션을 기다리면 품절자도 스레드를 기다린다.
  기본 Tomcat 스레드(200개)에서 품절 p95는 5.7초였고, 가상 스레드에서는 1.5초였다. 이 선택은 2-2 재측정에서 정한다.
