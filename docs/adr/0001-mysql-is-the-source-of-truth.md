# ADR-001: 최종 판단은 MySQL이 한다

- 상태: 채택
- 날짜: 2026-11-24

## 맥락
드롭 오픈 순간에는 재고보다 수십 배 많은 요청이 몇 초 안에 몰린다. 빠르게 거르는 것과, 판매 결과가 절대 틀리지 않는 것 사이에서 균형을 잡아야 한다.
이 프로젝트의 약속은 "장애 중에도 초과판매 0건, 중복결제 0건"이다. 그래서 장애가 났을 때 무엇이 진실인지가 먼저 정해져 있어야 한다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| Redis만으로 재고 관리 (Lua 원자 연산) | 매우 빠름, 핫 로우 잠금 없음 | 비동기 복제라 장애 조치(failover) 때 마지막 차감이 사라질 수 있음 → 초과판매. 주문·결제와 한 트랜잭션으로 묶을 수 없음 |
| Kafka 이벤트 소싱 | 처리량, 재처리 가능 | 1단계 범위를 크게 넘는 복잡도. "지금 남은 재고"를 바로 답하기 어려움 |
| **MySQL이 최종 판단, 앞단 캐시는 1차 관문일 뿐** | 트랜잭션, CHECK·UNIQUE 제약, 커밋된 것은 사라지지 않음 | 행 하나에 쓰기가 몰리면 처리량 상한이 생김 |

## 결정
재고, 1인 한도, 주문·결제 상태의 최종 판단은 MySQL이 한다.
- 모든 상태 변경은 조건부 UPDATE 한 번이고, 영향 행이 0이면 실패다 (ADR-002, 003, 005).
- `CHECK (remaining_qty BETWEEN 0 AND total_qty)`, `payment.order_id UNIQUE` 같은 제약을 마지막 방어선으로 둔다. 코드에 버그가 있어도 DB가 거절한다 (트러블슈팅 001).
- 2단계의 Redis는 "통과시켜도 되는 사람"을 거르는 1차 관문일 뿐이다. Redis가 틀려도 MySQL이 막는다. Redis가 죽으면 느려질 뿐 틀리지 않는다.

## 결과와 포기한 것
- **처리량 상한**: 1단계 기준선(`docs/reports/phase1-baseline.md`)에서 재고 1,000개가 팔리는 데 약 5초, 초당 약 200건이었다.
  커넥션 풀이나 디스크 동기화를 바꿔도 같았다. `drop_event` 행 하나의 잠금이 상한이다.
- 대신 구매자 5,000명 측정에서도 초과판매, 5xx, 정합성 위반은 0이었다.
- 2단계 목표는 상한을 높이는 것이 아니라 **DB에 닿는 요청 수를 재고 수준으로 줄이는 것**이다. MySQL은 계속 최종 판단을 맡는다.
- 정합성 체커(`docs/consistency-checks.sql`)는 MySQL 상태만 보고 판정한다. 이 결정이 있어서 체커가 단순하다.
