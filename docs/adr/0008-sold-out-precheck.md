# ADR-008: 품절 선판정은 잠금 없는 읽기로

- 상태: 채택
- 날짜: 2026-11-25

## 맥락
1단계 기준선에서 품절 응답이 성공 응답보다 느렸다 (구매자 3,000명: 품절 p50 6.3초, 성공 p50 3.4초).
REPEATABLE READ에서는 `UPDATE ... WHERE remaining_qty >= ?`의 조건이 거짓이어도 행을 잠근다.
그래서 품절된 사람도 재고 행의 잠금 줄에 서서 자기 차례를 기다렸다가 0행 결과를 받았다 (ADR-002).

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **트랜잭션 안에서 잠금 없는 읽기로 남은 재고 확인 후, 모자라면 바로 `SOLD_OUT`** | 이미 읽던 드롭 정보 조회에 열 하나 추가. 서버 여러 대에서도 그대로 동작 | 매진 전에 도착한 요청에는 효과가 없음 |
| 주문 트랜잭션을 READ COMMITTED로 | InnoDB semi-consistent read로 조건이 거짓인 잠긴 행은 기다리지 않음 | 매진 전에는 조건이 참이라 똑같이 기다림. 트랜잭션마다 격리 수준이 달라져 설명 비용이 큼 |
| JVM 안 품절 플래그 | DB 왕복도 없음 | 서버마다 따로 알아야 하고, 만료·취소로 재고가 돌아오면 플래그를 지워야 함 |

## 결정
멱등 키 확인 바로 뒤, 재고 UPDATE 전에 잠금 없는 일관된 읽기로 `remaining_qty`를 보고, 요청 수량보다 적으면 `SOLD_OUT`을 돌려준다.
멱등 재요청을 먼저 처리하므로, 이미 성공한 주문의 재시도가 매진 뒤에 품절로 보이지 않는다.
이 판단이 틀리는 방향은 "남았는데 품절로 보임"(읽은 직후 만료·취소로 재고가 돌아온 경우)뿐이다. 초과판매를 막는 판단은 여전히 조건부 UPDATE가 한다.
`cutline.order.sold-out-precheck`로 끌 수 있게 해 같은 날 같은 환경에서 켠 상태와 끈 상태를 비교했다.

## 결과와 포기한 것
- 측정 (구매자 3,000명, 재고 1,000개, 같은 날 같은 환경, 각 3회의 중앙값, `docs/reports/phase2-1-sold-out-precheck.md`):

  | | 품절 p50 / p95 | 결제 p95 | 재고 행 잠금 대기 합계 |
  | --- | --- | --- | --- |
  | 선판정 끔 | 7.30 / 8.61초 | 6.78초 | 62.8초 |
  | **선판정 켬** | **6.02 / 6.60초** | **4.73초** | **45.5초** |
  | READ COMMITTED (선판정 끔) | 7.03 / 7.67초 | 5.51초 | 47.6초 |

- 품절 p95는 23%, 결제 p95는 30% 줄었다. 하지만 **품절 응답은 여전히 매진 시각(약 5.6초) 근처에 온다.**
  구매자 대부분이 오픈 1초 안에 도착하므로, 그 시점에는 재고가 남아 있어 선판정을 통과하고 줄에 선다.
  선판정이 없애는 것은 매진 뒤에 줄에서 빠져나오는 시간(약 1초)뿐이다.
- 결론: 품절 응답을 100ms 아래로 내리려면 "누가 이길지"를 DB 잠금 줄 밖에서 정해야 한다. 이것이 Redis 관문(2-2)의 이유다.
  선판정은 Redis 장애 시 폴백 경로에 남는다.
- READ COMMITTED는 같은 이유로 매진 전 요청에는 효과가 없어 채택하지 않았다.
- 경합 테스트: `SoldOutPrecheckTest`. 다른 트랜잭션이 재고 행을 잠근 채로 품절 주문이 3초 안에 `SOLD_OUT`을 받는다. 선판정을 끄면 이 테스트가 시간 초과로 실패하는 것을 확인했다.
