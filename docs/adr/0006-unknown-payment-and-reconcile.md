# ADR-006: 결제 응답 유실은 UNKNOWN 상태와 PG 조회로 확정

- 상태: 채택
- 날짜: 2026-11-24

## 맥락
PG 승인 요청은 외부 네트워크 호출이다. 타임아웃이 났다고 해서 결제가 안 됐다는 뜻은 아니다. PG는 승인했는데 응답만 사라졌을 수 있다.
이것을 실패로 처리하면 "돈은 나갔는데 주문은 만료"가 생긴다. 무작정 다시 승인하면 이중 결제가 생길 수 있다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 타임아웃 = 실패 | 단순 | 돈은 나갔는데 상품은 없음 |
| PG 호출 동안 DB 트랜잭션 유지 | 상태가 한 번에 바뀜 | PG가 느려지면 커넥션·잠금을 쥔 채 대기. 기준선에서 본 커넥션 고갈이 결제 경로에도 생김 |
| 타임아웃이면 바로 재승인 | 사용자 경험 | PG 멱등성에 전적으로 의존. 응답이 계속 없으면 무한 재시도 |
| **결제 상태를 기록하며 진행 + 모르면 UNKNOWN + 백그라운드 조회로 확정** | 각 단계가 짧은 트랜잭션. 어떤 지점에서 죽어도 복구 가능 | 상태가 늘고, 클라이언트는 202(확인 중)를 처리해야 함 |

## 결정
`PaymentService.confirm`의 흐름:
1. 트랜잭션 1: 주문 행 `FOR UPDATE` → 소유자·상태·점유 시간·금액 검증 → 결제 `REQUESTED` 기록
2. PG 승인 호출 (트랜잭션 밖). 주문 ID가 PG 쪽 멱등 키다.
3. 결과에 따라 처리한다.
   - 승인: 트랜잭션 2에서 결제 `APPROVED` + 주문 `PAID` (조건부). 그 사이 주문이 만료·취소됐으면 **PG 승인을 취소**(보상)하고 409로 응답한다.
   - 거절: 결제를 `FAILED`로 바꾼다. 점유 시간 안이면 다른 결제수단으로 다시 시도할 수 있다.
   - 응답 없음: 결제를 `UNKNOWN`으로 두고 202로 응답한다. 이 주문은 만료되지 않는다 (ADR-005).

`PaymentReconciler`(5초 주기)는 다음을 처리한다.
- `UNKNOWN`과 30초 넘게 남은 `REQUESTED`(서버가 PG 호출 도중 죽은 경우)를 PG 조회로 확정한다.
- "승인됐는데 주문이 PAID가 아닌 결제"를 찾아 보상 취소를 다시 시도한다. 구매자 취소 후 환불도 이 경로가 안전망이다.

잠금 규칙: 주문과 결제를 함께 바꾸는 트랜잭션은 항상 주문 행을 먼저 잠근다. 없는 결제 행을 `FOR UPDATE`로 찾지 않는다.
없는 행에 `FOR UPDATE`를 걸었을 때 갭 잠금 때문에 200건 중 57건이 데드락으로 실패했다 (트러블슈팅 003).

## 결과와 포기한 것
- 시나리오 테스트 12개가 아래를 각각 재현한다 (`PaymentConfirmTest`).
  - 응답 유실, 요청 유실, 조회 실패
  - PG 승인 도중 만료, 보상 취소 실패, 서버 다운
- 만료 직전 200명 결제, PG 장애 30%, 만료 스케줄러 2대를 섞은 테스트에서 다음을 확인했다 (`PaymentRaceTest`, 5회).
  - PG에 남은 승인 = PAID 주문 수, 주문당 승인 ≤ 1
  - 환불 누락 0, 미해결 결제 0
- 포기한 것: 클라이언트가 202를 받으면 주문 조회로 결과를 기다려야 한다. 최종 상태까지 최대 수 초가 걸린다(복구 작업 주기).
- 3단계에서 실제 PG(토스페이먼츠)로 바꿀 때, `stale-requested-after`(30초)가 실제 HTTP 타임아웃보다 충분히 긴지 확인한다. 웹훅도 같은 전이 코드로 처리한다.
