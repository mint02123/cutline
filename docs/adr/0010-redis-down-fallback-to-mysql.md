# ADR-010: Redis 장애 시 MySQL 경로로 폴백

- 상태: 채택
- 날짜: 2026-11-25

## 맥락
Redis 관문(ADR-009)이 멈추거나 데이터를 잃었을 때 드롭을 어떻게 할지 정해야 한다.
판매를 멈추면 안전하지만, 한정판 드롭에서 수 분의 중단은 사실상 판매 실패다.
반대로 Redis 없이 계속 팔면 관문이 걸러 주던 요청이 모두 MySQL로 간다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| Redis 장애 시 주문 중단 (503) | 가장 단순, DB 보호 | 장애 동안 판매 0 |
| **MySQL 경로로 폴백 (선판정 + 조건부 UPDATE), 서버당 동시 진입 제한** | 정합성은 그대로, 판매 계속 | 느림. 관문을 거친 경우보다 품절 응답이 늦음 |
| Redis Sentinel/Cluster로 장애 자체를 줄임 | 폴백 빈도 감소 | 로컬 단계에서는 과함. 5단계(ElastiCache)에서 다룬다. 장애 처리는 어차피 필요 |

## 결정
- Redis 호출이 실패(연결 실패, 시간 초과 500ms)하면 그 요청은 MySQL 경로로 처리한다. 정합성은 1단계와 같은 근거(조건부 UPDATE, DB 제약)로 지켜진다.
- 실패 직후 2초 동안은 Redis를 부르지 않는다. 그러지 않으면 요청마다 500ms 시간 초과를 기다린다. 2초가 지나면 다시 시도한다.
- MySQL 경로는 서버당 동시 20개로 제한한다. 자리가 없으면 2초 기다린 뒤 `503 TOO_BUSY`. 관문이 걸러 주던 요청이 한꺼번에 커넥션과 스레드를 잡지 않게 한다.
- Redis 실패는 `GateUnavailableException`으로 바꿔, MySQL 실패와 섞이지 않게 한다.

## 결과와 포기한 것
- 테스트(`GateFailureTest`, `GateFallbackLimitTest`):
  - Redis를 멈춘(docker pause) 채 1,000명이 재고 100개에 몰려도 정확히 100건, 나머지는 모두 `SOLD_OUT`.
  - 멈춘 동안 19건 처리에 걸린 시간이 건너뛰기 없이 예상되는 9.5초의 절반 미만.
  - Redis 데이터 유실(FLUSHALL) 뒤 MySQL에서 다시 적재, 이미 산 회원은 MySQL 한도가 막고 토큰은 반환.
  - 동시 진입 한도를 넘은 요청은 0.2초 뒤 503.
- **테스트로 알게 된 것: 시간 초과로 포기한 Lua 호출은 취소되지 않는다.** 명령은 이미 Redis 소켓에 들어가 있어서, 멈춤이 풀리면 그대로 실행된다.
  그 요청들은 이미 MySQL 경로로 처리됐으므로 토큰만 줄어든다(덜 파는 쪽). 1,000명 테스트에서는 복구 직후 토큰이 0까지 줄었다.
  반대로 포기한 반환 명령이 나중에 실행되면 토큰이 돌아오는데, 반환은 이미 일어난 일을 반영하는 것이라 맞는 결과다.
  어느 쪽이든 재동기화(5초 주기)가 MySQL 기준으로 맞춘다. 관문 Lua가 "통과"만 하고 MySQL은 건드리지 않게 설계한 덕분에 늦게 실행돼도 더 팔 수 없다.
- **측정으로 알게 된 것: Redis가 돌아온 직후 토큰이 MySQL보다 많다.** 멈춘 동안 MySQL 경로로 팔린 주문은 토큰을 쓰지 않기 때문이다.
  첫 측정(오픈 2초 뒤 3초 정지)에서 복구 직후 토큰 247~374개, 남은 재고 0이었고 3번 모두 정합성 체커에 걸렸다.
  그대로 두면 관문이 없는 재고로 사람을 들여보내고, 그 요청이 MySQL 품절 뒤 토큰을 돌려줘 토큰이 줄지 않는다.
  고친 방법: MySQL 경로로 주문을 만든 드롭을 커밋 뒤 표시하고, 관문을 다시 쓰기 전에 토큰을 MySQL 남은 재고로 낮춘다.
  또 관문 통과 뒤 MySQL 품절이면 토큰을 돌려주지 않고 낮춘다 (ADR-009). 고친 뒤 3번 모두 토큰 0, 체커 통과.
- 측정(구매자 3,000명, 재고 1,000개, 오픈 2~5초 Redis 정지, 3회 중앙값): 품절 p95 5.50초, 주문 성공 p95 4.92초, 5xx 0, 503 0, 정합성 통과.
  관문을 끈 상태(품절 p95 6.03초)와 비슷해, 장애 동안은 2-1 수준으로 돌아간다는 예상과 맞았다. `docs/reports/phase2-2-redis-gate.md`
- 포기한 것: 장애 동안 품절 응답은 1단계 수준으로 느리다. 동시 진입 한도에 걸린 요청은 503을 받고 다시 시도해야 한다.
- 다시 볼 조건: 5단계에서 Redis를 관리형(복제본 포함)으로 옮기면 장애 빈도와 복구 시간을 다시 잰다. 건너뛰기 2초와 동시 20개는 그때 측정으로 조정한다.
