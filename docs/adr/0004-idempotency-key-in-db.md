# ADR-004: 멱등 키는 주문과 같은 DB 트랜잭션에 저장

- 상태: 채택
- 날짜: 2026-11-24

## 맥락
오픈 순간 사용자는 버튼을 여러 번 누르고, 앱과 네트워크는 타임아웃 뒤 재시도한다. 같은 요청이 두 번 처리되면 한 사람이 두 개를 잡게 된다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| Redis `SET NX`로 키 선점 | 빠름 | 주문 트랜잭션과 따로 놂. 키는 저장됐는데 주문은 롤백되거나, 그 반대가 가능 |
| 앱 메모리 캐시 | 가장 빠름 | 서버가 여러 대면 무의미, 재시작하면 사라짐 |
| **`idempotency_key` 테이블, 주문과 같은 트랜잭션** | 주문과 키가 함께 커밋·롤백. 동시 중복은 PK 잠금에서 기다렸다가 저장된 응답을 받음 | 핫 트랜잭션에 쓰기 2번 추가 |

## 결정
- `POST /api/drops/{id}/orders`는 `Idempotency-Key` 헤더가 필수다. 키는 `(member_id, idem_key)`가 PK다.
- 트랜잭션 맨 앞에서 `IN_PROGRESS`로 INSERT하고, 끝에서 응답 본문과 함께 `COMPLETED`로 바꾼다.
- 같은 키가 다시 오면 다음과 같이 처리한다.
  - `COMPLETED`: 저장된 응답을 그대로 돌려준다.
  - 처리 중: 409 `REQUEST_IN_PROGRESS`
  - 요청 내용(해시)이 다름: 422 `IDEMPOTENCY_KEY_REUSED`
- 실패(품절 등)하면 키도 롤백되므로, 같은 키로 다시 시도할 수 있다.
- 결제 확정은 별도 키를 두지 않았다. 주문당 결제가 하나뿐이라(`payment.order_id UNIQUE`) 주문 ID가 자연스러운 멱등 키다. PG에도 주문 ID를 멱등 키로 보낸다 (ADR-006).

## 결과와 포기한 것
- 같은 키로 50번 동시에 보내도 주문 1건이고, 50개 응답이 모두 같은 주문 ID다 (`OrderConcurrencyTest`).
- 기준선 문장 통계에서 키 INSERT·UPDATE는 각각 평균 0.2~0.3ms였다. 핫 로우를 쥐는 시간에 더해지는 비용이다.
- 아직 없는 것: 오래된 키 정리(TTL). 2단계에서 보관 기간과 정리 배치를 정한다.
