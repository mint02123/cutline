# ADR-005: 점유 만료는 스케줄러 + 조건부 상태 전이로

- 상태: 채택
- 날짜: 2026-11-24

## 맥락
주문은 재고를 잡은 채 결제를 기다린다(`hold_minutes`, 기본 10분). 결제하지 않으면 재고와 한도를 돌려줘야 다음 사람이 살 수 있다.
서버가 여러 대여도 한 주문의 재고가 두 번 돌아오면 안 된다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 조회할 때 만료 처리 (lazy) | 스케줄러 불필요 | 아무도 조회하지 않으면 재고가 안 돌아옴 |
| MySQL 이벤트 스케줄러 | 앱과 무관하게 동작 | 로직이 DB에 숨고 테스트가 어려움. 결제 상태 확인 같은 규칙을 넣기 불편 |
| 지연 큐 (Redis, Kafka) | 정확한 시각에 실행 | 1단계에 인프라 추가. 메시지 유실 대비가 따로 필요 |
| 리더 선출 후 한 대만 실행 (ShedLock 등) | 중복 작업 없음 | 잠금 테이블과 설정 추가. 정합성은 여전히 조건부 전이로 지켜야 함 |
| **모든 서버가 1초마다 실행 + 조건부 상태 전이** | 단순. 어느 서버가 몇 대 돌든 결과가 같음 | 같은 주문을 여러 서버가 집어 헛수고할 수 있음 |

## 결정
`OrderExpirer`가 1초마다 `OrderExpiryService.expireDue()`를 실행한다. 주문 하나당 트랜잭션 하나로 처리한다.
```sql
UPDATE orders SET status = 'EXPIRED' ...
WHERE id = ? AND status = 'PENDING_PAYMENT' AND hold_expires_at <= ?
  AND NOT EXISTS (SELECT 1 FROM payment WHERE order_id = orders.id AND status = 'UNKNOWN')
```
- 1행이 바뀐 경우에만 같은 트랜잭션에서 재고와 한도를 되돌린다 (`HoldRelease`, 잠금 순서 `drop_event` → `member_drop_quota`).
- **결제가 UNKNOWN인 주문은 만료하지 않는다.** 돈이 나갔을 수 있기 때문이다. 결제 복구 작업이 결과를 확정한 뒤 처리한다 (ADR-006).
- 한 주문이 실패해도 나머지는 계속 처리한다. 실패 수(`failureCount`)를 노출해 테스트가 삼켜진 데드락을 잡게 했다.
- 구매자 취소도 같은 방식(조건부 전이 + `HoldRelease`)이라 만료와 취소가 동시에 와도 복구는 한 번이다.

## 결과와 포기한 것
- 스케줄러 4대가 주문 300건을 동시에 만료해도 처리 합계가 정확히 300이고 재고 복구도 한 번씩이었다. 만료와 신규 주문 300명이 동시에 진행돼도 데드락은 0이었다 (`OrderExpiryTest`).
- 취소 100건과 만료 2대가 동시에 와도 복구는 한 번씩이었다 (`OrderCancelTest`).
- 포기한 것: 만료가 최대 약 1초(+처리 시간) 늦다. PG 승인 중(REQUESTED)인 주문도 만료될 수 있다. 이 경우 결제 확정 쪽이 승인을 취소한다(보상, ADR-006).
- 다시 볼 조건: 서버 수가 늘어 헛수고가 DB 부하로 보이면 주문 ID 범위로 나누거나 리더 선출을 넣는다.
