# ADR-011: 요청 처리는 가상 스레드로

- 상태: 채택
- 날짜: 2026-11-25

## 맥락
Redis 관문(ADR-009)은 품절자를 MySQL 앞에서 수백 마이크로초 만에 돌려보낼 수 있다. 그런데 플랫폼 스레드(Tomcat 기본 200개)에서는
관문을 통과한 요청 1,000개가 커넥션 풀(10개)을 기다리며 요청 스레드를 모두 쥐었다. 품절자도 스레드를 얻을 차례를 기다려,
품절 p95가 6.03초(관문 끔)에서 4.78초로 21%밖에 줄지 않았다. 줄이 DB 커넥션 앞에서 요청 스레드 앞으로 옮겨 간 것이다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 플랫폼 스레드 그대로 | 산 사람의 응답이 가장 빠름 (주문 성공 p50 3.21초) | 품절자가 스레드를 기다림 (품절 p95 4.78초) |
| Tomcat 스레드 수 늘리기 | 설정 하나 | 스레드당 메모리. 몇 배로 늘려도 오픈 순간 동시 요청(수천)을 다 받지 못함 |
| 관문을 별도 스레드 풀이나 비동기(WebFlux)로 | 품절 경로를 확실히 분리 | 주문 경로 전체를 다시 짜야 함. 1단계 코드와 테스트를 버림 |
| **가상 스레드** (`spring.threads.virtual.enabled`) | 설정 하나, 기다리는 요청이 스레드를 붙잡지 않음 | 커넥션 풀을 기다리는 요청 수에 상한이 사라짐 |

## 결정
가상 스레드를 기본으로 켠다. 같은 시간대 3회씩 잰 중앙값 (구매자 3,000명, 재고 1,000개, `docs/reports/phase2-2-redis-gate.md`):

| | 품절 p95 | 주문 성공 p50 / p95 | 결제 p95 | 매진까지 |
| --- | --- | --- | --- | --- |
| 플랫폼 스레드 | 4.78초 | 3.21 / 5.59초 | 3.62초 | 6.71초 |
| 가상 스레드 | **0.94초** | 4.45 / 6.03초 | **3.08초** | 7.58초 |

2단계의 첫 목표는 품절된 사람을 즉시 돌려보내는 것이고, 3,000명 중 2,000명이 품절자다.

- `synchronized` 안에서 I/O를 기다리면 Java 21 가상 스레드가 캐리어 스레드를 붙잡는다(pinning). 우리 코드에서 유일했던
  `GateResync.resync()`의 `synchronized`를 `ReentrantLock`으로 바꿨다. 라이브러리(HikariCP, MySQL Connector/J, Lettuce) 안쪽은 확인하지 않았다.
  2-3 측정에서 JFR `jdk.VirtualThreadPinned` 이벤트로 실제 pinning이 있는지 본다.

## 결과와 포기한 것
- 포기한 것: 산 사람이 더 기다린다. 주문 성공 p50이 1.2초, 매진까지가 0.9초 늘었다. 플랫폼 스레드 200개가 우연히 해 주던 입장 제한이 사라져,
  관문을 통과한 1,000개가 한꺼번에 커넥션 풀을 기다리기 때문으로 본다(CPU 표본은 뜨지 않아 확인하지 못함).
- 이 비용은 2-3 대기열이 다룬다. 대기열은 커넥션을 기다리는 요청 수를 입장 속도로 묶는다. 2-3 측정에서 가상 스레드를 끈 경우와 다시 비교한다.
- 다시 볼 조건: 대기열 뒤에도 주문 성공 p95가 플랫폼 스레드보다 나쁘면, 입장 속도 대신 주문 경로에 동시 실행 제한(세마포어)을 둘지 본다.
