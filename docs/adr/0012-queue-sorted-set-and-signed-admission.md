# ADR-012: 대기열은 Redis sorted set, 입장은 서명 토큰, Redis 장애 시 줄을 건너뜀

- 상태: 채택 (입장 속도는 9일차 측정으로 다시 정함)
- 날짜: 2026-11-26

## 맥락
2-2 관문 뒤에도 재고 행 하나를 쥐는 시간(약 5ms) 때문에 주문은 초당 약 200건이 상한이다. 오픈 순간 3,000명이 한꺼번에 주문하면
관문을 통과한 1,000명이 커넥션 풀 앞에 줄을 서서 산 사람의 응답 p95가 6초를 넘었다(ADR-011). 이 대기를 서버가 쥐고 있지 않고
"내 앞에 312명" 화면으로 바꾸려면, 줄을 세우고 MySQL이 처리할 수 있는 만큼만 들여보내야 한다.

정해야 할 것은 세 가지다.
1. 줄과 순번을 어디에 두는가
2. 입장한 사람을 주문 API가 어떻게 알아보는가
3. Redis가 죽으면 대기열을 어떻게 하는가 (2-2 목표: Redis 장애 중에도 판매, 정합성 위반 0)

## 고려한 대안

**줄**
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **Redis sorted set, 점수는 Lua 안의 순번(seq)** | `ZRANK` O(log N)으로 내 앞 인원, `ZPOPMIN`으로 앞에서 꺼내기. 서버 여러 대에서도 순번이 겹치지 않음 | Redis를 잃으면 줄도 잃음 |
| sorted set, 점수는 도착 시각(ms) | 구현이 가장 단순 | 같은 ms에 수백 명이 와서 동점이 생기고, 서버마다 시계가 달라 순서가 서버 시계에 좌우됨 |
| Kafka 등 메시지 큐 | 내구성 | "내 앞에 몇 명"을 물을 수 없음. 3단계 전에 Kafka를 들이게 됨 |
| MySQL 테이블 | 내구성, 정합성 한곳 | 줄 서기 자체가 오픈 순간 MySQL 쓰기 3,000건. 없애려던 병목을 다시 만듦 |

**입장 확인**
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **HMAC 서명 토큰 (드롭, 회원, 만료 시각)** | 검증에 Redis가 필요 없음. Redis가 죽어도 이미 입장한 사람은 주문 가능 | 만료 전에는 철회할 수 없음 |
| Redis에서 입장 기록 조회 | 철회 가능, 일회용으로 만들 수 있음 | 주문마다 Redis 호출이 하나 늘고, Redis가 죽으면 입장한 사람도 주문 불가 |

토큰을 일회용으로 만들지 않았다. 같은 회원이 만료 전에 토큰을 다시 써도 그 회원이 살 수 있는 양은 MySQL 1인 한도가 정하고,
결제 실패 뒤 다시 주문하는 정상 흐름을 막지 않기 위해서다. 다른 회원의 토큰은 서명에 회원 id가 들어가 있어 쓸 수 없다.

**Redis 장애 시**
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 503으로 판매 중단 | 순서가 끝까지 공정 | 장애 시간만큼 판매가 멈춤. 2-2 목표와 어긋남 |
| **줄을 건너뛰고 바로 입장 토큰 발급** | 판매가 이어짐. 주문은 2-2의 MySQL 폴백 경로(서버당 동시 20건)가 받음 | 장애 동안은 도착 순서가 아니라 먼저 자리를 얻은 순서. 몰리면 503 `TOO_BUSY` |

## 결정
- 줄은 `queue:{dropId}` sorted set, 점수는 `queue:{dropId}:meta`의 `seq`를 Lua 안에서 하나씩 늘린 값이다.
  줄 서기와 순번 조회는 MySQL에 닿지 않는다. 드롭마다 처음 한 번만 오픈 시각을 MySQL에서 적재한다.
- 입장 스케줄러(100ms)가 지난 입장 이후 흐른 시간 × 초당 입장 인원만큼 `ZPOPMIN`한다. 기준 시각이 Redis에 있어
  서버 여러 대의 스케줄러가 함께 돌아도 전체 입장 속도는 설정값이고, 같은 사람을 두 번 꺼내지 않는다.
  스케줄러가 멈췄다 돌아와도 1초치까지만 몰아서 들인다.
- 매진 표시는 MySQL 남은 재고 기준으로 스케줄러가 주기마다 맞춘다. 표시되면 새 줄 서기는 409 `SOLD_OUT`, 줄에 남은 사람은
  `SOLD_OUT` 상태를 보고 입장이 멈춘다. 만료·취소로 재고가 돌아오면 표시를 지우고 같은 자리에서 입장을 재개한다.
- 입장 토큰은 HMAC-SHA256 서명 토큰이고 만료는 2분이다. 주문 API는 `X-Admission-Token`을 확인한다.
  만료된 사람은 다시 줄을 서면 맨 뒤에 선다. 입장 순서가 자리 기반이 아니라 속도 기반이라, 만료된 사람의 몫은 따로 넘기지 않아도
  다음 주기의 입장으로 이어진다.
- Redis에 닿지 못하면 줄 서기와 순번 조회가 곧바로 `ADMITTED`(`bypassed: true`)와 토큰을 준다. 주문은 관문도 Redis에 닿지 못하므로
  ADR-010의 MySQL 폴백 경로로 간다. 이 상태에서 8명이 재고 5개에 몰리는 테스트로 5건 판매, 3건 품절, 정합성 위반 0을 확인했다.

## 결과와 포기한 것
- **공정성은 Redis가 살아 있는 동안만 보장한다.** 장애 동안은 서버당 동시 처리 제한을 먼저 얻은 사람이 산다.
- **Redis 데이터를 잃으면 줄도 잃는다.** 서 있던 사람은 다시 줄을 서야 하고 순번은 새로 매겨진다. 입장 토큰은 서명이라 살아남는다.
- 매진 표시는 스케줄러 주기(100ms)만큼 늦을 수 있다. 그 사이 입장한 사람은 주문에서 2-2 관문의 `SOLD_OUT`을 받는다.
- 입장 속도 200명/초는 1단계 측정치에서 가져온 가설이다. 입장한 사람의 주문 p95 1초를 넘지 않는 가장 큰 값을 9일차 측정(`drop-queue.js`)으로 정한다.
- 서명 키는 설정값(`cutline.queue.admission.secret`)이다. 운영에서는 환경 변수로 주입하고, 키를 바꾸면 발급된 토큰(최대 2분치)이 모두 무효가 된다.
- 봇이 여러 계정으로 줄을 서는 것은 막지 않는다 (설계 문서 열린 질문, 6단계에서 다룸).
