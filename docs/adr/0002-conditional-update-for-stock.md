# ADR-002: 재고 차감은 조건부 UPDATE 한 번으로

- 상태: 채택
- 날짜: 2026-11-24

## 맥락
수천 명이 같은 드롭의 재고 행 하나를 동시에 줄인다. "남은 재고 확인 → 차감" 사이에 다른 요청이 끼어들면 초과판매가 난다.

## 고려한 대안
| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 비관적 락: `SELECT ... FOR UPDATE` 후 `UPDATE` | 익숙한 패턴 | 왕복 2번 동안 잠금을 쥠. 읽은 값으로 판단하는 코드가 앱에 생김 |
| 낙관적 락: `version` 비교 후 실패 시 재시도 | 잠금 없음 | 경합이 심하면 대부분 충돌. 1,000명이 동시에 오면 재시도 폭주로 오히려 느려짐 |
| **조건부 UPDATE: `SET remaining = remaining - ? WHERE id = ? AND status = 'OPEN' AND opens_at <= ? AND remaining >= ?`** | 확인과 차감이 한 문장, 왕복 1번. 결과는 영향 행 수로 판단 | 실패 이유(품절인지 오픈 전인지)를 따로 알아내야 함 |

## 결정
조건부 UPDATE 한 문장으로 차감하고, 영향 행이 0이면 실패로 본다.
실패 이유는 트랜잭션 앞에서 읽어 둔 드롭 정보로 `SOLD_OUT`과 `DROP_NOT_OPEN`을 구분한다.
`opens_at <= now`를 조건에 넣어, 오픈 스케줄러가 늦더라도 오픈 전에 팔리지 않게 한다.

**잠금 순서 규칙**: 재고 차감은 주문 트랜잭션에서 가장 먼저 한다.
처음에는 핫 로우 잠금을 짧게 쥐려고 맨 뒤에 뒀다. 그런데 한도 테이블 INSERT의 외래 키 검사가 `drop_event`에 공유 잠금을 먼저 걸었다.
그 결과 1,000명 중 82%가 S→X 승격 데드락으로 실패했다 (트러블슈팅 002). 지금은 X 잠금을 처음에 잡는다.

## 결과와 포기한 것
- 1,000명 동시 주문 테스트에서 재고 100개에 정확히 100건, 데드락 0건 (`OrderConcurrencyTest`).
- 재고 행 X 잠금을 한도 upsert, 주문 INSERT, 커밋까지 쥔다. 기준선에서 주문 한 건당 약 5ms였고, 이것이 처리량 상한이 됐다.
- **REPEATABLE READ에서는 조건이 거짓인 UPDATE도 행을 잠근다.** 그래서 품절된 사람도 같은 줄에 서고, 품절 응답 중간값이 6~7초였다.
  2단계 첫 개선으로 "재고 0이면 잠금 없는 읽기로 바로 품절"을 넣고 같은 스크립트로 다시 잰다.
- 다시 볼 조건: Redis 관문 뒤에도 매진 시간이 목표에 못 미치면 재고 행 분할(행 N개로 나눠 경합 분산)을 검토한다.
